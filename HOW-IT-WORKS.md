# How this profile is built

Everything on the profile page is an SVG generated by the scripts in this
repository. There is no image editor in the loop, no third-party stat-card
service, and no hardcoded numbers. A scheduled workflow re-renders the whole
thing every night from the GitHub API.

## Why generate it instead of using the usual services

Profile READMEs are usually assembled from hosted card services. That works
until it doesn't: those services rate-limit, they go down, and every profile
using them looks the same. Generating the assets in-repo means the page cannot
break because of someone else's outage, and it looks like nothing else.

## The pieces

```
profile.config.json   name, tagline, theme, prose — the only file most edits touch
scripts/
  config.mjs      loads and validates that file, with errors that name the fix
  pixelfont.mjs   a 5x7 bitmap font, drawn by hand, rendered to SVG paths
  sprites.mjs     the agent, the ghost and Claude's mascot, as layered bitmaps
  theme.mjs       four palettes, language colours, deterministic PRNG
  fx.mjs          CRT treatment, panels, meters, the digit roll
  cards.mjs       the six compositions
  data.mjs        one GraphQL call plus the public contribution graph
  readme.mjs      README.md, built from the same snapshot as the cards
  generate.mjs    ties it together
```

Using this for your own profile is [SETUP.md](SETUP.md); handing the job to an
AI assistant is [AGENTS.md](AGENTS.md).

Run it locally:

```bash
GITHUB_TOKEN=$(gh auth token) npm run build
```

Then open `preview.html` to see every asset with its animations, and use the
replay button to watch them start over.

To iterate on the visuals without touching the network, `npm run build:cached`
re-renders from the snapshot in `.cache/`.

## The look

The reference is a real arcade cabinet in attract mode — CRT scanlines,
chromatic fringing at the edges of large text, phosphor bloom, a blinking
`PRESS START` — rather than anything neon or cyberpunk.

The palette is deliberately warm. The obvious choice for "retro tech" is cyan
and violet on black, which is also the most recognisable signature of
generated design work. Real cabinets were lit by amber marquees and warm
phosphor, so amber leads here, red and pink accent, and green is held back for
live data so it never reads as decoration.

| Token | Hex | Role |
|---|---|---|
| `bg` | `#14101f` | Deep indigo-black. Tinted, never pure black. |
| `ink` | `#f4ecd8` | Warm bone white — aged phosphor, never `#fff` |
| `amber` | `#ffb627` | Dominant. Marquee gold |
| `red` | `#ef3d3d` | Cabinet red — chromatic fringe |
| `magenta` | `#ff5da2` | Ghost pink |
| `green` | `#7ee787` | Phosphor green — data only |
| `blue` | `#4d9bff` | Maze blue — structure |

One rule governs the rest: **the hero is the only climax.** It powers on like a
tube warming up; everything below it is quieter on purpose.

Three more palettes ship alongside it — `phosphor` (green terminal), `synth`
(hot pink) and `ice` (cool blue) — selected with one line in the config. Each is
a complete set rather than a hue rotation, because a palette that works is a set
of relationships, not a filter. `C` in `theme.mjs` is a live object that
`applyTheme()` swaps at start-up, so no drawing code knows themes exist.
Anything that captures a colour at module load would silently freeze the
default; that is why `languageColor` builds its fallback list per call.

## Decisions worth knowing about

**Text is drawn, not typeset.** SVGs embedded in a README cannot load web fonts,
and system font stacks render at different metrics on every platform, which
would shift the layout. So every character is a bitmap in `pixelfont.mjs`,
emitted as run-length-merged rectangles and collapsed into a single `<path>`
per text block. That cut the largest asset from 264 KB to about 107 KB.

**The resting state is the truth.** The score digits spin up like a cabinet
tallying a score, but the real digit sits first in each column at offset zero.
An untransformed column already shows the correct number, so anyone who has
animations turned off — or whose browser never runs them — sees real data rather
than the random decoy that a naive implementation would leave on screen.

**Contribution numbers come from the public profile page**, not from the
GraphQL calendar. GraphQL only ever reports what the requesting token may see,
which in a scheduled workflow means public repositories only. Reading the same
graph a visitor sees means the profile can never contradict itself, and it picks
up private contributions automatically if the account owner chooses to publish
them.

**No rendered figure may depend on which token generated it.** This follows from
the point above and cost a redesign to get right. The obvious stats to show are
the commit / pull request / issue split, and GraphQL hands them over readily —
but it reports them relative to the caller. A token with `read:user` scope sees
1039 commits where the workflow's repo-scoped token sees 746, so those numbers
would have flipped back and forth on every scheduled run, and "1244
contributions" sitting next to "746 commits" does not even cohere. The cards now
show only what the calendar and the public repository list can supply: active
days, best day, longest streak, contributions per week. The GraphQL counts are
still fetched, and `data.mjs` marks them as deliberately unrendered so nobody
reaches for them again.

**Randomness is seeded.** Star positions and the digit decoys come from a
seeded PRNG, so re-running the generator produces byte-identical output when the
data has not changed. Without that, every nightly run would commit a diff full
of shuffled stars.

**Language bars use a square-root curve.** One language at 56% would leave
everything below fourth place as an empty track under linear scaling. The exact
percentage is printed next to every bar, so the compression costs no accuracy.

## Rendering constraints this had to work around

An SVG referenced from a README is loaded in what the spec calls *secure
animated mode*. In practice:

| Works | Does not work |
|---|---|
| CSS `@keyframes` in an internal `<style>` | Any external reference — fonts, images, stylesheets |
| SMIL (`<animate>`, `<animateTransform>`) | `<a>` links inside the SVG |
| SVG filters, `mix-blend-mode` | JavaScript |
| `<use href="#id">` with fill inheritance | `@font-face` pointing at a URL |

Two traps worth recording:

- **Filter regions clip.** The default is `-10%` to `120%` of the object
  bounding box, which cuts a Gaussian blur off square. The bloom filter here
  declares a much wider region, and sets `color-interpolation-filters="sRGB"`
  because the SVG default of linearRGB washes warm colours out.
- **`transform-origin` is `0 0` on SVG elements**, not `center`. Setting
  `transform-box: fill-box` alone does nothing; both are required, or the CRT
  power-on unfolds from the corner instead of the middle.

Because links inside an SVG are inert, every project on the cabinet screen also
gets a real text link underneath it in the README.

## The nightly refresh

`.github/workflows/refresh.yml` runs on a cron, regenerates every asset and the
README, and commits only if something actually changed. It authenticates with
the workflow's built-in token — no personal access token, no secrets to rotate.

`raw.githubusercontent.com` serves these files with a five-minute cache, so an
update is visible almost immediately. The images are referenced by relative
path, which means they never pass through GitHub's camo proxy and never hit its
long-lived cache.
